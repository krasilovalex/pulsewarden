# Pulsewarden — границы MVP


## 1. Краткое описание

Pulsewarden — self-hosted платформа мониторинга доступности публичных сайтов и HTTP API.

Система автоматически выполняет HTTP- и HTTPS-проверки по расписанию, измеряет время ответа, сохраняет историю результатов, определяет устойчивые сбои и отправляет уведомления через Telegram или webhook.

Главная задача первого MVP — реализовать полный и надёжный путь от создания HTTP-монитора до обнаружения инцидента и отправки уведомления.

## 2. Целевой пользователь

Основные пользователи Pulsewarden:

- backend-разработчики;
    
- владельцы небольших self-hosted проектов;
    
- небольшие технические команды;
    
- DevOps- и SRE-инженеры;
    
- владельцы публичных сайтов и HTTP API.
    

Пользователю необходимо знать:

- доступен ли его сервис в данный момент;
    
- когда начался сбой;
    
- сколько длился сбой;
    
- как часто происходили ошибки;
    
- как изменяется время ответа;
    
- восстановился ли сервис после инцидента.
    

Pulsewarden ориентирован на пользователей, которым нужен контролируемый мониторинг без установки агента на целевой сервер.

## 3. Проблема пользователя

Публичный сайт или API может перестать отвечать, начать возвращать неправильный статус либо работать слишком медленно.

Без автоматического мониторинга пользователь может узнать о проблеме только от клиентов или после ручной проверки.

Одиночная сетевая ошибка не всегда означает реальный сбой. Если уведомлять о каждой ошибке, система будет создавать слишком много ложных тревог.

Пользователю нужен инструмент, который:

- регулярно проверяет ресурс;
    
- сохраняет результаты каждой проверки;
    
- отличает единичную ошибку от устойчивого сбоя;
    
- создаёт один инцидент вместо множества одинаковых;
    
- уведомляет о начале проблемы;
    
- уведомляет о восстановлении;
    
- позволяет просмотреть историю и причину ошибки.
    

## 4. Функции MVP

### Пользователи

В MVP пользователь может:

- зарегистрироваться;
    
- войти в систему;
    
- работать только со своими мониторами;
    
- получить список своих мониторов.
    

### HTTP-мониторы

Пользователь может:

- создать HTTP- или HTTPS-монитор;
    
- указать URL;
    
- выбрать метод `GET` или `HEAD`;
    
- указать ожидаемый HTTP-статус;
    
- установить интервал проверки;
    
- установить timeout;
    
- включить или приостановить монитор;
    
- изменить настройки монитора;
    
- удалить или архивировать монитор.
    

### Выполнение проверок

Система:

- автоматически запускает проверки по расписанию;
    
- ограничивает количество одновременно выполняемых проверок;
    
- не создаёт неограниченное количество goroutines;
    
- применяет timeout к каждой проверке;
    
- измеряет длительность проверки;
    
- ограничивает размер HTTP response body;
    
- сохраняет результат выполнения;
    
- классифицирует сетевые ошибки;
    
- корректно обрабатывает отмену через context;
    
- поддерживает graceful shutdown.
    

### Результаты проверок

Для каждой проверки сохраняются:

- идентификатор монитора;
    
- время запуска;
    
- время завершения;
    
- итоговый статус;
    
- HTTP-статус ответа;
    
- длительность проверки;
    
- тип ошибки;
    
- безопасное диагностическое сообщение;
    
- уникальный execution ID.
    

Монитор может иметь состояние:

- `UP`;
    
- `DOWN`;
    
- `DEGRADED`;
    
- `PAUSED`.
    

### Инциденты

Система:

- открывает инцидент после трёх последовательных результатов `DOWN`;
    
- закрывает открытый инцидент после двух последовательных результатов `UP`;
    
- не создаёт новый инцидент при каждой ошибке;
    
- допускает только один активный инцидент одного типа для одного монитора;
    
- сохраняет время открытия и закрытия инцидента;
    
- защищает обработку результатов от дублирования.
    

### Уведомления

В MVP поддерживаются:

- Telegram;
    
- generic webhook.
    

Система отправляет уведомления:

- при открытии инцидента;
    
- при восстановлении ресурса и закрытии инцидента.
    

Для временных ошибок доставки применяются:

- ограниченное количество повторных попыток;
    
- exponential backoff;
    
- jitter;
    
- сохранение истории попыток.
    

### Безопасность

Система должна:

- разрешать только HTTP- и HTTPS-адреса;
    
- запрещать loopback-адреса;
    
- запрещать приватные IP-адреса;
    
- запрещать link-local адреса;
    
- проверять IP после DNS-резолюции;
    
- повторно проверять адрес перед сетевым подключением;
    
- проверять каждую цель HTTP redirect;
    
- ограничивать количество redirect;
    
- запрещать URL со встроенными credentials;
    
- ограничивать размер response body;
    
- не записывать токены и секреты в логи;
    
- валидировать пользовательский ввод;
    
- применять rate limiting к API.
    

### Наблюдаемость

MVP содержит:

- structured logging;
    
- Prometheus-метрики;
    
- Grafana dashboard;
    
- health endpoint;
    
- readiness endpoint;
    
- базовый tracing;
    
- `pprof`, недоступный из публичной сети.
    

### Развёртывание

Проект должен:

- запускаться через Docker Compose;
    
- использовать PostgreSQL;
    
- применять миграции базы данных;
    
- получать конфигурацию через environment variables;
    
- иметь Makefile;
    
- иметь CI;
    
- содержать OpenAPI-описание;
    
- содержать README с инструкцией запуска.
    

## 5. Что не входит в MVP

В первый MVP сознательно не входят:

- TCP probe;
    
- DNS probe;
    
- отдельный мониторинг срока действия TLS-сертификата;
    
- VPS-agent;
    
- сбор CPU, RAM и disk usage;
    
- мониторинг systemd-сервисов;
    
- распределённые probe-ноды;
    
- проверки из нескольких регионов;
    
- подтверждение сбоя большинством probe-нод;
    
- Kafka;
    
- Redis без доказанной необходимости;
    
- Kubernetes;
    
- публичные status pages;
    
- email- и SMS-уведомления;
    
- организации и команды;
    
- сложная RBAC-модель;
    
- SSO;
    
- billing;
    
- maintenance windows;
    
- сложные escalation policies;
    
- browser monitoring;
    
- выполнение пользовательских скриптов;
    
- произвольные HTTP-методы и request body;
    
- сложные JSONPath-выражения;
    
- SLA, SLO и error budgets;
    
- гарантия exactly-once доставки.
    

Для фоновых задач и уведомлений используется модель at-least-once с идемпотентной обработкой.

## 6. Критерии завершения MVP

MVP считается завершённым, если выполняются все следующие условия.

1. Пользователь может зарегистрироваться и пройти аутентификацию.
    
2. Пользователь может создать HTTP- или HTTPS-монитор через REST API.
    
3. Пользователь не может получить или изменить монитор другого пользователя.
    
4. Активные мониторы автоматически проверяются по заданному расписанию.
    
5. Количество одновременно выполняемых проверок ограничено настройкой worker pool.
    
6. Каждая завершённая проверка сохраняется в PostgreSQL и отображается в истории монитора.
    
7. Для каждой проверки сохраняются HTTP-статус, latency и категория ошибки.
    
8. Три последовательных результата `DOWN` создают ровно один активный инцидент.
    
9. Дополнительные результаты `DOWN` во время активного инцидента не создают новые одинаковые инциденты.
    
10. Два последовательных результата `UP` закрывают активный инцидент.
    
11. При открытии инцидента отправляется уведомление в Telegram или webhook.
    
12. При закрытии инцидента отправляется уведомление о восстановлении.
    
13. Повторная обработка одного execution ID не создаёт второй результат, инцидент или логическое уведомление.
    
14. Задание, worker которого завершился до окончания обработки, может быть повторно получено после истечения lease.
    
15. Loopback-, private- и link-local адреса отклоняются HTTP probe.
    
16. Каждый HTTP redirect проходит повторную SSRF-проверку.
    
17. Размер читаемого response body ограничен.
    
18. При завершении процесса новые задания перестают приниматься, а уже начатые завершаются или отменяются через context.
    
19. Система запускается одной командой через Docker Compose.
    
20. Миграции применяются автоматически или отдельной документированной командой.
    
21. CI запускает unit-тесты и integration-тесты.
    
22. CI или отдельная документированная команда запускает `go test -race ./...`.
    
23. Prometheus получает метрики выполненных проверок, ошибок, latency, активных workers, очереди, инцидентов и уведомлений.
    
24. Grafana содержит dashboard с основными метриками системы.
    
25. Health endpoint показывает, что процесс запущен.
    
26. Readiness endpoint учитывает доступность обязательных зависимостей.
    
27. Секреты Telegram и webhook не выводятся в логах.
    
28. README содержит воспроизводимую инструкцию запуска проекта.
    
29. README содержит демонстрационный сценарий: создание монитора, имитация сбоя, открытие инцидента, восстановление и закрытие инцидента.
    
30. В README перечислены известные ограничения MVP и угрозы, которые ещё не закрыты полностью.
