# ADR-001: Application Architecture for MVP

## Status

Accepted.

## Context

Pulsewarden должен выполнять несколько разных типов работы:

- принимать REST API-запросы;
- управлять пользователями и HTTP-мониторами;
- планировать проверки;
- выполнять сетевые проверки с ограниченной конкурентностью;
- сохранять результаты;
- обрабатывать переходы состояний инцидентов;
- отправлять уведомления.

У API и фоновой обработки разные профили нагрузки и разные требования к завершению работы.

API должен быстро отвечать на пользовательские запросы и не зависеть от длительности сетевых проверок. Worker выполняет потенциально медленные и ненадёжные внешние операции, использует worker pool и должен корректно восстанавливать задания после сбоя.

На этапе MVP проект разрабатывается одним разработчиком и разворачивается через Docker Compose. Разделение каждого модуля на самостоятельный микросервис увеличит количество сетевых контрактов, инфраструктуры и сценариев отказа до появления необходимости в таком усложнении.

При этом размещение API, scheduler и всех workers в одном неразделённом процессе затруднит независимый перезапуск, управление ресурсами и последующее масштабирование фоновой обработки.

## Decision

Pulsewarden реализуется как модульный монолит в одном Git-репозитории.

Проект будет содержать два запускаемых процесса:

1. `Pulsewarden-api`
   - предоставляет REST API;
   - выполняет аутентификацию и авторизацию;
   - управляет HTTP-мониторами;
   - предоставляет историю проверок и инцидентов;
   - предоставляет health и readiness endpoints.

2. `Pulsewarden-worker`
   - планирует HTTP-проверки;
   - получает задания из PostgreSQL;
   - выполняет проверки через bounded worker pool;
   - сохраняет результаты;
   - запускает incident engine;
   - обрабатывает transactional outbox;
   - отправляет уведомления.

Оба процесса:

- собираются из одного Go module;
- используют общие доменные пакеты;
- используют одну PostgreSQL database;
- используют один набор миграций;
- версионируются и выпускаются вместе;
- не взаимодействуют друг с другом через внутренний HTTP или gRPC API.

PostgreSQL является основным способом координации процессов в MVP.

Границы внутренних модулей должны отражать бизнес-возможности, а не технические слои. Доменная логика не должна зависеть от HTTP handlers, конкретного SQL-драйвера или реализации логирования.

API и worker должны иметь независимые точки входа и отдельные lifecycle:

- собственный root context;
- обработку системных сигналов;
- graceful shutdown;
- отдельную конфигурацию;
- отдельные health/readiness проверки;
- отдельные метрики процессов.

Решение не запрещает позже выделить модуль в отдельный сервис. Такое выделение должно происходить только при наличии измеримой причины и оформляться отдельным ADR.

## Consequences

### Positive

- локальный запуск остаётся простым;
- API и worker можно перезапускать независимо;
- сетевые проверки не выполняются внутри процесса API;
- worker можно масштабировать отдельно от API;
- отсутствуют внутренние сетевые вызовы между бизнес-модулями;
- транзакционные операции можно выполнять в одной PostgreSQL database;
- integration-тесты не требуют запуска множества сервисов;
- границы модулей можно проверить внутри одного Go module;
- архитектура допускает последующее выделение отдельных сервисов.

### Negative

- API и worker связаны общей схемой базы данных;
- изменения доменной модели требуют согласованного выпуска процессов;
- ошибка в общем пакете может повлиять на оба бинарника;
- PostgreSQL становится центральной зависимостью и точкой координации;
- независимое версионирование API и worker в MVP не поддерживается;
- границы модулей обеспечиваются структурой кода и code review, а не сетевой изоляцией.

### Operational implications

- Docker Compose должен запускать отдельные контейнеры API и worker;
- миграции должны выполняться до перехода процессов в состояние readiness;
- остановка worker должна прекращать получение новых заданий;
- уже полученные задания должны завершаться в пределах shutdown timeout либо освобождаться после истечения lease;
- недоступность worker не должна делать API недоступным для операций чтения и управления мониторами;
- readiness каждого процесса должна учитывать только обязательные для него зависимости.

## Alternatives Considered

### Single process

API, scheduler и workers запускаются в одном бинарнике и одном процессе.

Вариант проще на старте, но отклонён как целевая архитектура MVP, потому что:

- фоновые проверки делят ресурсы с API;
- процессы нельзя независимо перезапускать;
- сложнее отдельно масштабировать workers;
- graceful shutdown объединяет разные типы работы;
- сбой probe-кода увеличивает риск недоступности API.

Этот вариант может временно использоваться только в ранних локальных экспериментах, но не является целевой схемой Docker Compose.

### Full microservice architecture

API, scheduler, probe workers, incident engine и notification workers становятся отдельными сервисами.

Вариант отклонён для MVP, потому что потребует:

- внутренних HTTP, gRPC или message contracts;
- версионирования сообщений;
- дополнительных deployment units;
- распределённой трассировки между всеми компонентами;
- обработки большего числа сетевых отказов;
- усложнения локальной разработки и integration-тестов;
- решения задач распределённой согласованности раньше, чем они действительно возникнут.

### Serverless scheduled functions

Каждая проверка запускается отдельной облачной функцией по расписанию.

Вариант отклонён, потому что проект должен:

- быть self-hosted;
- запускаться через Docker Compose;
- демонстрировать реализацию scheduler и bounded worker pool;
- не зависеть от конкретного облачного провайдера;
- позволять контролировать сетевую политику probe-процесса.
