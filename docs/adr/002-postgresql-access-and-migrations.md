# ADR-002: PostgreSQL Access and Schema Migrations

## Status

Accepted.

## Context

Pulsewarden использует PostgreSQL как основное постоянное хранилище и
механизм координации фоновых процессов.

В PostgreSQL будут храниться:

- пользователи;
- HTTP-мониторы;
- расписание проверок;
- задания и их lease;
- результаты проверок;
- состояние мониторов;
- инциденты;
- transactional outbox;
- задания и попытки доставки уведомлений.

С базой данных работают как минимум два процесса:

- `pulsewarden-api`;
- `pulsewarden-worker`.

Оба процесса могут работать одновременно и в будущем могут запускаться
в нескольких экземплярах.

Необходимо определить:

- PostgreSQL-драйвер;
- способ управления connection pool;
- механизм миграций;
- владельца lifecycle соединений;
- правила работы с транзакциями;
- поведение health и readiness endpoints;
- способ запуска integration-тестов.

## Decision

### PostgreSQL driver

Приложение использует:

`github.com/jackc/pgx/v5`

Для управления пулом соединений используется:

`github.com/jackc/pgx/v5/pgxpool`

Pulsewarden работает только с PostgreSQL и не ставит целью поддержку
нескольких SQL-диалектов.

Использование PostgreSQL-специфичного API допускается, когда это даёт
практическую пользу проекту. В частности, в проекте планируется
использовать:

- `FOR UPDATE SKIP LOCKED`;
- PostgreSQL error codes;
- `RETURNING`;
- advisory locks, если для них появится обоснованная задача;
- PostgreSQL-specific data types;
- batch operations;
- transactional outbox.

Выбор `pgx` не означает, что пакет `database/sql` является неподходящим.
Он является допустимым универсальным интерфейсом, но дополнительная
абстракция над разными SQL-драйверами Pulsewarden не требуется.

### Connection pool ownership

Каждый запускаемый процесс создаёт и закрывает собственный
`pgxpool.Pool`.

Пул:

- не хранится в глобальной переменной;
- создаётся в composition root процесса;
- передаётся инфраструктурным компонентам явно;
- закрывается во время graceful shutdown;
- не создаётся внутри каждого repository;
- не скрывается за package-level singleton.

API и worker используют независимые пулы, даже если подключаются к одной
базе данных.

Параметры пула задаются через environment variables.

Минимальный набор настроек:

- PostgreSQL DSN;
- максимальное число соединений;
- минимальное число idle-соединений;
- максимальное время жизни соединения;
- максимальное время простоя соединения;
- timeout первоначального подключения;
- timeout readiness-проверки.

Значения по умолчанию должны быть консервативными и учитывать общее
ограничение PostgreSQL на число соединений.

### Startup

При запуске процесса:

1. загружается и валидируется конфигурация;
2. создаётся logger;
3. парсится конфигурация `pgxpool`;
4. создаётся connection pool;
5. с отдельным timeout выполняется `Ping`;
6. только после успешной инициализации запускаются HTTP server или
   worker loops.

Если начальное подключение не удалось, процесс завершается с ненулевым
exit code.

Процесс не должен бесконечно ждать PostgreSQL во время старта.

Повторные попытки запуска контейнера являются обязанностью среды
развёртывания. Для Docker Compose может использоваться restart policy
и healthcheck.

### Shutdown

Во время graceful shutdown:

1. процесс прекращает принимать новую работу;
2. активным операциям даётся ограниченное время завершиться;
3. фоновые циклы останавливаются;
4. PostgreSQL pool закрывается после остановки компонентов, которые его
   используют.

После вызова `pool.Close()` новые запросы к пулу не выполняются.

### Context and query timeout

Каждая операция с PostgreSQL принимает `context.Context`.

Запрещено использовать `context.Background()` внутри repository для
обычных запросов.

Repository получает context от вызывающего слоя.

HTTP-запросы используют request context.

Фоновые задачи используют context конкретной операции с установленным
deadline.

Отмена context должна прерывать ожидание соединения из pool и выполнение
запроса, насколько это поддерживается драйвером и PostgreSQL.

Общий timeout процесса не заменяет timeout отдельной database operation.

### Transactions

Транзакция создаётся на уровне application use case, которому нужна
атомарность нескольких операций.

Repository не должен незаметно открывать самостоятельную транзакцию,
если вызывающий код ожидает атомарность нескольких repository calls.

Транзакция должна:

- принимать context;
- всегда завершаться через `Commit` или `Rollback`;
- выполнять `Rollback` через `defer` как защиту от раннего выхода;
- возвращать ошибку `Commit`;
- не игнорировать ошибки;
- оставаться короткой;
- не включать внешние HTTP-запросы;
- не включать отправку Telegram или webhook;
- не удерживаться во время длительной сетевой проверки.

Изменение инцидента и создание outbox event должны выполняться в одной
транзакции.

Повтор транзакции после serialization failure или deadlock не
добавляется глобально. Retry допускается только для конкретных
идемпотентных операций и должен иметь ограничение числа попыток.

### Query ownership

SQL-запросы находятся рядом с PostgreSQL-реализацией соответствующего
repository.

Доменный слой:

- не импортирует `pgx`;
- не знает о таблицах;
- не знает о SQL error codes;
- не принимает `pgx.Tx` в публичных доменных интерфейсах.

На первом этапе SQL пишется вручную.

ORM и query builder не добавляются, пока не появится конкретная проблема,
которую они решают.

### Schema migrations

Для управления схемой используется:

`github.com/golang-migrate/migrate/v4`

Миграции хранятся в:

`migrations/`

Каждое изменение схемы содержит два файла:

- `<version>_<name>.up.sql`;
- `<version>_<name>.down.sql`.

Пример:

- `000001_initialize_schema.up.sql`;
- `000001_initialize_schema.down.sql`.

Для новых миграций используются последовательные числовые версии.

Миграции содержат обычный PostgreSQL SQL.

Go migrations в MVP не используются.

### Migration execution

Миграции не запускаются автоматически из `pulsewarden-api` или
`pulsewarden-worker`.

Они выполняются отдельным migration command или отдельным контейнером.

Для Docker Compose порядок запуска должен обеспечивать:

1. доступность PostgreSQL;
2. успешное применение миграций;
3. запуск API и worker.

Причины не применять миграции внутри каждого приложения:

- несколько экземпляров могут одновременно попытаться изменить схему;
- приложение получает лишние права на DDL;
- долгие миграции затрудняют диагностику старта;
- ошибка миграции смешивается с ошибкой запуска приложения;
- deployment и schema change имеют разные lifecycle.

В локальном окружении Makefile предоставляет отдельные команды:

- `make migrate-up`;
- `make migrate-down`;
- `make migrate-version`;
- `make migrate-create`.

Команда полного отката всех миграций не должна случайно выполняться
обычным development workflow.

### Migration rules

После попадания миграции в основную ветку её существующие SQL-файлы не
редактируются.

Исправление выполняется новой миграцией.

Каждая destructive migration должна рассматриваться отдельно.

Для потенциально больших таблиц заранее оцениваются:

- длительность блокировки;
- необходимость backfill;
- возможность поэтапного изменения;
- совместимость старой и новой версии приложения;
- необходимость создания индекса без длительной блокировки.

MVP не заявляет zero-downtime migrations для всех изменений.

### Health and readiness

`GET /healthz` не обращается к PostgreSQL.

Он подтверждает только, что процесс запущен и HTTP server способен
обработать запрос.

`GET /readyz` проверяет готовность обязательных зависимостей.

Для API обязательной зависимостью является PostgreSQL.

Для worker PostgreSQL также является обязательной зависимостью, но его
readiness будет предоставляться отдельным служебным HTTP server либо
другим механизмом, который будет зафиксирован позже.

Readiness-проверка PostgreSQL:

- использует короткий timeout;
- выполняет `Ping`;
- не запускает бизнес-запросы;
- не применяет миграции;
- не раскрывает клиенту DSN или текст внутренней ошибки.

При недоступности PostgreSQL readiness возвращает `503 Service
Unavailable`.

Ошибка PostgreSQL записывается в structured log без credentials.

### Integration tests

Integration-тесты работают с настоящим PostgreSQL.

SQLite и in-memory SQL implementation не используются как замена
PostgreSQL, потому что проект зависит от PostgreSQL-specific поведения.

Integration-тесты должны проверять:

- применение миграций;
- repository queries;
- constraints;
- unique indexes;
- транзакционные инварианты;
- row-level locking;
- `FOR UPDATE SKIP LOCKED`;
- поведение concurrent workers.

На первом этапе тестовая база запускается через Docker Compose.

Добавление testcontainers рассматривается отдельно, если ручное
управление тестовым PostgreSQL станет неудобным.

Каждый integration-тест должен:

- получать изолированные данные;
- не зависеть от порядка запуска тестов;
- корректно очищать созданные записи;
- иметь timeout;
- не использовать production database;
- иметь явный opt-in через build tag или отдельную команду.

### Secrets

PostgreSQL DSN считается секретом.

Запрещено:

- коммитить настоящий DSN;
- логировать полный DSN;
- возвращать DSN в HTTP-ответах;
- добавлять пароль в trace attributes;
- включать credentials в текст readiness-ошибки.

Репозиторий содержит только безопасный `.env.example`.

## Consequences

### Positive

- приложение использует прямой PostgreSQL driver;
- pool поддерживает конкурентную работу API и workers;
- отсутствует глобальное состояние подключения;
- lifecycle соединений остаётся явным;
- миграции отделены от запуска приложения;
- SQL остаётся видимым и контролируемым;
- integration-тесты проверяют реальное поведение PostgreSQL;
- архитектура позволяет использовать PostgreSQL job queue и
  transactional outbox.

### Negative

- код привязан к PostgreSQL;
- часть ошибок драйвера нужно классифицировать явно;
- SQL-запросы и scanning пишутся вручную;
- migration tool использует отдельный lifecycle;
- разработчику нужен запущенный PostgreSQL для integration-тестов;
- изменение схемы требует согласования с версиями API и worker.

### Risks

- слишком большие connection pools могут исчерпать лимит PostgreSQL;
- долгие транзакции могут увеличить lock contention;
- забытый query timeout может удерживать ресурсы;
- некорректная down migration может удалить данные;
- readiness может создать дополнительную нагрузку при слишком частом
  polling;
- миграция может успешно примениться, но быть несовместимой со старым
  бинарником;
- retry неидемпотентной транзакции способен создать дубли.

Эти риски должны контролироваться конфигурацией, метриками,
integration-тестами и отдельным review миграций.

## Alternatives Considered

### database/sql

Стандартный пакет предоставляет общий интерфейс для SQL database drivers.

Вариант отклонён не из-за недостатка надёжности, а потому что Pulsewarden
использует только PostgreSQL и планирует применять его специфические
возможности.

Дополнительная переносимость между SQL databases не является требованием
MVP.

### ORM

Рассматривалось использование ORM для моделей и запросов.

Вариант отклонён для MVP, потому что:

- важные запросы scheduler и incident engine будут PostgreSQL-specific;
- необходимо явно понимать locking и transaction boundaries;
- автоматически созданные запросы усложнят анализ производительности;
- текущий объём CRUD не оправдывает дополнительный слой.

### Automatic migrations on application startup

Рассматривалось применение миграций при запуске API.

Вариант отклонён, потому что schema migration и application startup
имеют разные failure modes и требования к правам доступа.

### Go-based migrations

Рассматривались миграции в виде Go-функций.

Вариант отклонён для MVP. Изменения схемы должны быть представлены
читаемым PostgreSQL SQL.

Go migration может быть рассмотрена отдельно для сложного data migration,
которое нельзя разумно выразить SQL.

### SQLite for integration tests

Вариант отклонён, потому что SQLite не воспроизводит PostgreSQL locking,
error codes, `SKIP LOCKED`, типы и ограничения.

### Testcontainers from the first iteration

Вариант пока отложен.

Docker Compose даёт достаточно простой и видимый способ запуска
PostgreSQL. Testcontainers будет добавлен, если он заметно упростит
изоляцию и CI.
